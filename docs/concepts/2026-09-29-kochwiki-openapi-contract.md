# Kochwiki OpenAPI Contract Generation

## Status

Draft under discussion. Agreed scope: every Kochwiki-owned FastAPI endpoint, including routes Angular does not currently call and the recipe-presentation resolver used by AI Service. Every Kochwiki JSON response consumed by Angular receives generated runtime validation. Fixed response objects reject undocumented fields, assuming coordinated backend and frontend rollout. The AI Service's conversation API contract concept is the baseline for the contract strategy, not an implementation dependency. FastAPI's default 422 shape is restored, domain 404/409 errors use `detail` and are declared in OpenAPI, `/meta/version` declares its plain-text response, and delete routes declare bodyless 204 responses. Checked-in TypeScript types and Zod Mini schemas now cover the complete Kochwiki OpenAPI document. Foodstuff CRUD uses generated request and response types and validates successful JSON responses. Foodstuff labels and unit choices are now owned by Angular; the metadata endpoints and fetching service have been removed. User selection and restoration now use generated types and strict runtime validation. Recipe list, active detail, and specific version loading now use generated response types and strict nested runtime validation. Recipe writes now use generated request types and validate all five JSON mutation responses; ambiguous write failures withhold success feedback and navigation.

Kochwiki's resolver success schema is now closed at every object level, and its checked-in OpenAPI and Zod validators have been regenerated. The agreed Python consumer direction is a Kochwiki-owned standalone package containing shared Pydantic API models, distributed as versioned wheels through public GitHub Releases. The first extraction slice is implemented under `backend/contract`: Kochwiki imports the shared definitions, a local wheel can be installed independently, and CI verifies that wheel before the existing OpenAPI drift check. Validation and wire behavior remain unchanged. Stricter validation, release distribution, AI Service migration, and cross-repository compatibility protection remain to be implemented. The user has reverted AI Service's consumer-owned OpenAPI work. ## Context

Kochwiki's FastAPI routes declare Pydantic request models and response models for recipes, foodstuffs, users, and the recipe-presentation resolver. FastAPI serves OpenAPI at `/api/openapi.json`. Angular calls Kochwiki through `/api` with `HttpClient` and now uses generated wire types and runtime validators. The resolver is also called by the separately deployed AI Service; the browser's `/ai/api/v1` conversation route is a relay to that service, not a Kochwiki backend API.

The AI Service concept establishes a useful pattern: backend models define the HTTP contract; the exported OpenAPI document drives checked-in TypeScript types and runtime validators; the transport validates received JSON while retaining its existing request and error behavior. Kochwiki has a different transport and audience, so that pattern needs adaptation rather than direct copying.

## Problem

Handwritten wire interfaces can drift from FastAPI's shapes. `HttpClient.get<T>()` asserts a type without validating the received body. Angular's former foodstuff create/update methods accepted `Partial<Foodstuff>` even though the backend uses separate create and update schemas; they now use generated request types. The foodstuff delete method previously promised a numeric response although the route returns 204 with no body; it now returns `Promise<void>`. AI Service's resolver still builds requests manually and validates responses against handwritten Python models.

Kochwiki now uses FastAPI's default request-validation response, `{ detail: [validation issues] }`, and returns domain 404/409 errors as `{ detail: string }`. Applicable domain errors are declared per route in OpenAPI. The HTTP status is carried by the response status line. FastAPI's generated validation-issue schema permits optional `input` and `ctx` and additional fields, so error validators must not impose the strict fixed-object policy used for Kochwiki-owned success DTOs. The plain-text version endpoint and bodyless 204 responses still need to survive generation with their actual media types and semantics.

## Proposed Direction

Treat Kochwiki's FastAPI models and route declarations as the source of truth for all Kochwiki-owned HTTP endpoints. Cover Angular-used routes, the recipe-presentation resolver consumed by AI Service, and currently unused routes such as recipe history, ingredient and step lists, and user mutations. Keep the AI Service conversation contract owned and generated in the AI Service repository; Kochwiki should use the published chat UI transport for that boundary rather than generate a second client from the relayed paths.

Make OpenAPI describe actual successful and expected failed responses before relying on generated output. Preserve FastAPI response validation on JSON success paths and its default 422 behavior. Model and validate domain error bodies sent through direct `JSONResponse`. Keep 204 responses bodyless and `/meta/version` as text. Check concrete route behavior against the exported document, especially recipe decimals, nullable values, and resolver responses.

Generate checked-in TypeScript request and response types from a reproducible `app.openapi()` export so Angular builds do not depend on a running backend. Replace handwritten wire interfaces at the backend service boundary, while keeping UI-only view models and mapping functions where they express actual presentation needs. Add the existing generation drift check to release/CI when the toolchain is available there. Hey API `0.99.0`, matching the AI Service's pinned version, passed the Kochwiki trial for decimal numbers, nullable responses, plain text, bodyless 204, and resolver types.

Use generated runtime validators for every Kochwiki JSON response consumed by Angular, after verifying they preserve the existing numeric, nullable, and nested recipe shapes. Reject undocumented fields on fixed response objects rather than silently stripping them. Allow dynamic keys only where the OpenAPI schema explicitly models a map. Validate before data reaches recipe editing, proposal mapping, and draft saving. Keep Angular `HttpClient` and the existing service methods; generating a full HTTP client is not needed to eliminate duplicate models and unchecked responses. Classify malformed success bodies separately from HTTP failures without weakening the current 404/422 handling. The exact validator integration and UI error behavior remain to be decided. The plain-text version endpoint and bodyless 204 responses do not pass through JSON validators.

## Contract Boundaries

- Kochwiki owns recipe, foodstuff, user, version metadata, and recipe-presentation resolver shapes. The AI Service owns session, message, turn, and proposal-envelope shapes. The Nginx and Angular relays do not create a new contract source.
- The resolver is a service-to-service contract and deserves explicit coverage even if Angular does not call it directly. Its request and enriched response must agree with AI Service's expectations; generated Angular types alone cannot establish that.
- Backend and Angular changes in this repository roll out together. Strict response validation assumes neither side will serve an incompatible version during deployment. The resolver has a separate deployer and may need coordinated rollout when its wire shape changes.
- HTTP DTOs and UI domain models may differ. Generated types should replace duplicate wire definitions, not force backend-specific names and optionality through every component.
- Runtime validation checks JSON shape; it does not prove business rules, authorization, or that an AI proposal is safe to save. Proposal artifact validation remains at the AI Service boundary and Kochwiki's proposal-to-draft mapping.

## Alternatives Considered

- **Keep handwritten models and add contract tests:** small tooling cost, but dual definitions and unchecked HTTP responses remain.
- **Generate TypeScript types only:** catches compile-time drift but leaves runtime JSON unchecked. This may be a useful first delivery slice, not the complete direction.
- **Generate a full client:** would replace established Angular services and complicate their change notifications and error handling without a clear contract benefit.
- **Generate types and validators:** matches the AI Service baseline and addresses both drift and runtime shape checks, at the cost of generator workflow and browser dependency weight.

The Angular service boundary is the natural place to consume generated types and validators. ## Resolver Integration Direction

### Agreed producer-owned package

Extract Kochwiki's existing Pydantic API DTOs into an independently installable contract package in the Kochwiki repository. Kochwiki and compatible Python consumers import the same model definitions, validators, serializers, and enums. This is extraction into one authoritative source, not copying backend models into a distribution folder. No OpenAPI-to-Pydantic generation step is required. Kochwiki owns package maintenance, validation fidelity, and distribution because it owns the API. Future consumers with compatible Python and Pydantic versions can reuse the package; OpenAPI remains available for consumers choosing other languages or validation libraries. Angular's existing OpenAPI-to-TypeScript/Zod generation remains unchanged in direction.

Keep the package dependency surface small: Pydantic and the standard library, with an explicitly tested Python/Pydantic compatibility range. Include pure API validation such as field constraints and collection uniqueness, but keep database access, authorization, persistence checks, application services, and HTTP transport outside the package. The initial `kochwiki-contract` package lives under `backend/contract` using a `src/kochwiki_contract` layout, keeping the backend Docker build context unchanged. Public exports cover resolver request/response models, their ingredient/step models, `FoodstuffSummaryOut`, and `Unit`. Existing ingredient/step write bases and decimal serialization are also extracted to preserve shared definitions used by other Kochwiki routes. Backend schema modules import the same classes rather than wrapping or copying them. Preserve AI Service's immutable internal presentation/proposal models and map validated package DTOs into them rather than propagating wire models through the proposal pipeline.

The extraction deliberately preserves existing acceptance, constraints, nullable-field requirements, closed objects, and serialization. `py.typed` is included; local version `0.0.0` is not a published release. Python 3.13 and Pydantic 2.13 are the initial baseline, with backend checks on 2.13.4 and isolated wheel checks on 2.13.5. Release versioning and the broader support matrix remain open. Local development installs the package into the backend environment; both backend Dockerfiles and the CI contract job install it from the checkout. CI builds a wheel and runs standalone tests in an isolated environment containing only the package and its runtime dependencies. Those tests protect request constraints and uniqueness, current decimal coercion, required nullable fields, closed nested objects, numeric response serialization, enums, and empty collections. Backend/API tests pass and the complete OpenAPI/Angular generation check remains unchanged.

Tighten validation in Kochwiki as part of making these models suitable for consumers. Sharing the current definitions alone would not preserve the generator trial's strict wire checks: `JsonDecimal` accepts decimal strings despite serializing as JSON numbers, and other primitive fields permit coercion. Response validation must reject numeric strings, booleans used as numbers, incorrect types, missing required nullable fields, and undocumented fields on closed objects, while preserving legitimate backend construction from `Decimal`, numeric JSON serialization, nulls, enums, and nested/empty collections. Do not assume that enabling strict mode globally satisfies both backend construction and JSON validation. Retain extensibility for FastAPI's 422 issue bodies. Pure custom validators can be shared, but their behavior and dependencies must be appropriate for both producer and consumer.

Request acceptance may also be tightened deliberately. If decimal strings or other previously accepted coercions are rejected, treat that as an API contract change: update OpenAPI, regenerate Angular types and validators, and verify affected callers together. The exact validation mechanism and acceptance policy are still implementation decisions; this direction does not declare those changes already made. Tests must cover producer construction, actual endpoint JSON, consumer parsing, serialization, shared validators, and installation/import of the built package independently of the backend.

Build and distribute versioned wheels as assets of public GitHub Releases. AI Service declares a direct URL dependency on a specific released wheel and locks its dependencies; ordinary consumer installation requires neither Git nor a model generator. Record the source revision and corresponding API contract for each release and protect artifact integrity in the consumer's lock/update process. GitHub Packages has no Python/PyPI registry; PyPI is not required for the chosen distribution. Package name, versioning/tag convention, release triggers, and artifact provenance format remain to be decided. This records distribution intent, not authorization to publish a particular release.

Endpoint wiring remains manual: consumers associate HTTP method/path, request DTO, success DTO, and status/error handling using Kochwiki's OpenAPI or Swagger UI. Shared model sources do not derive or verify those associations automatically. Provide `py.typed` in the package and explicit consumer type checking so upgrades expose statically detectable incompatibilities; Python package builds alone do not type-check application code. Contract and integration tests must detect changed validation rules and other behavior that static types cannot express. Preserve AI Service's timeout and HTTP error classification, including non-retryable 404/422 responses and controlled parsing/mapping failures.

CI should verify package isolation and supported runtimes, the relationship between shared models, exported OpenAPI and actual route behavior, and AI Service's use of the released contract. Cross-repository compatibility tests should exercise actual resolver requests and responses with isolated environments. Installing a package does not establish that it matches a running Kochwiki deployment. Strict object validation can reject even an added response field; incompatible changes still require coordinated package upgrades and producer/consumer deployment. Automatic freshness monitoring and a compatibility window remain separate decisions.

### Superseded consumer-owned generation exploration

The following approach was explored and partly implemented before the producer-owned package decision. It is retained as historical evidence, not the current implementation direction; the user has since reverted the AI Service changes. With one consumer, either repository could own generation from OpenAPI; direct sharing avoids reconstructing Python models from schemas originally emitted by Pydantic and retains pure custom validation that OpenAPI does not express. The successful datamodel-code-generator trial establishes a viable alternative, but does not create a requirement to adopt it. Snapshot/provenance scripts are no longer planned as a model-generation dependency. Any future resolver expectations belong in contract tests rather than snapshot acquisition.

Deliver the resolver contract as one coherent direction across both repositories: accurate producer schemas, a versioned OpenAPI snapshot, deterministic Python wire models, consumer migration, and CI protection. Kochwiki remains authoritative for the resolver request, success response, and declared errors. The first step is implemented: `RecipePresentationOut`, `RecipePresentationIngredientOut`, and `RecipePresentationStepOut` now forbid additional fields, matching nested foodstuff summaries and resolver request objects. The wire fields, numeric serialization, required nullable values, and empty collections remain unchanged. Kochwiki's checked-in OpenAPI and generated Zod validators reflect the closed schemas. Regression tests cover rejection of undocumented fields at every response level, preserved numbers and nulls, required nullable fields, and actual endpoint responses. AI Service snapshot and generator tooling remain subsequent work.

AI Service will check in the complete reproducible Kochwiki OpenAPI export together with its source commit. Snapshot updates are explicit and reviewable. Ordinary generation and builds use that local snapshot rather than fetching a moving upstream schema or requiring a running Kochwiki backend. Provide separate snapshot-update, model-generation, and drift-check commands. Generate the resolver request, response, declared error models, and their referenced schemas through deterministic selection from the complete snapshot, without handwritten copies of those wire definitions or a generated full HTTP client.

The second step is implemented in AI Service through `backend/scripts/kochwiki_contract.py`. From its backend directory, `python scripts/kochwiki_contract.py update --commit <full-40-character-SHA>` fetches the checked-in export at `frontend/src/app/core/api/generated/openapi.json` from Kochwiki's public GitHub repository. The complete snapshot lives at `backend/contracts/kochwiki/openapi.json`; adjacent `provenance.json` records the repository, commit SHA, and source path. The initial revision is `39f3f9711b0fb3adcc37030d77429bddf6a08cee`, containing the completed resolver schema. `python scripts/kochwiki_contract.py check` compares the snapshot against that same pinned GitHub revision, permitting only LF/CRLF checkout conversion. Branches, tags, abbreviated SHAs, invalid provenance, missing files, invalid exports, and revisions without closed resolver response objects fail clearly. Fetch and validation failures preserve existing snapshot files; verification never rewrites them. Both commands use Python's standard library and public read access without a cross-repository secret or a local Kochwiki checkout. Kochwiki's existing CI generation gate verifies the upstream export against its backend, so snapshot acquisition does not require installing or running Kochwiki. Regression tests cover deterministic updates, pinned source URLs, rejected revisions, download and validation failures, missing or mismatched files, line endings, and command failure diagnostics. Local working-tree imports are deferred. Python model generation, resolver migration, and CI wiring follow in subsequent steps. Ordinary builds and future model generation remain offline with respect to Kochwiki.

Pin datamodel-code-generator 0.83.0 and its tooling dependencies, use the trialled configuration below, disable variable timestamps and paths in output, and check generated sources into AI Service. The third step also moves resolver-specific expectations out of the snapshot downloader into dedicated contract tests: snapshot acquisition retains basic document integrity checks, while tests protect the resolver operation, referenced schemas, and closed-object policy. This permits reviewing legitimate contract structure changes without treating them as download failures. The generator choice is agreed following the successful trial; permanent tests must retain coverage of reproducible output, numeric decimal responses, integer and fractional values, required nullable fields, nested collections, enums, and rejection of undocumented fields where the source schema forbids them. FastAPI's extensible validation-error fields must retain their documented openness rather than inherit a blanket strict-object policy. Generated validation must reject malformed JSON types rather than silently coerce them. OpenAPI does not express every backend business validator, so generated request models do not replace backend validation.

Migrate AI Service's resolver HTTP boundary to construct outgoing payloads with generated request models and validate incoming bodies with generated response models. Preserve its timeout and HTTP error classification behavior, including non-retryable 404/422 outcomes. The existing handwritten presentation models also serve as immutable proposal data, use tuple collections, and impose bounds absent from Kochwiki's response schema. Retain them as explicitly internal models and map validated wire responses into them. Keep internal constraints and proposal serialization stable; do not expose generated model naming, collection mutability, or weaker wire constraints throughout the proposal pipeline. Internal mapping failures must remain controlled resolver failures.

CI must check that generated Python models match the snapshot and that the snapshot matches the recorded Kochwiki revision. Compatibility tests must exercise the actual Kochwiki resolver with requests produced by the AI Service consumer and validate returned bodies through that consumer, covering decimals, independent nullability, empty and nested collections, and expected errors. Add malformed-response tests for missing fields, incorrect types, and undocumented fields, and verify that migration preserves proposal behavior. Test repositories in isolated environments so their identically named Python `app` packages do not collide. The exact cross-repository checkout and test mechanism remains to be selected; CI should gate AI Service image builds and publishing on these checks.

Checking the recorded upstream revision proves provenance and reproducibility, not freshness against Kochwiki's latest revision. Advancing that revision is an explicit contract update that reruns generation and compatibility checks. Incompatible resolver changes require coordinated producer and consumer deployment; snapshot pinning alone does not make mixed deployed versions compatible. Automatic upstream monitoring and any compatibility window remain separate decisions, rather than implicit live-schema fetching during builds.

## Python Generator Trial

These trial results belong to the superseded consumer-owned generation exploration. No Python generator is selected for the current shared-model package direction. Preserve the fidelity cases as useful regression requirements when extracting and tightening the original models; passing generated-model tests does not establish that the existing backend models already meet them.

OpenAPI Generator was the user's preferred candidate and was trialled at pinned version 7.25.0 against AI Service's complete snapshot from Kochwiki commit `39f3f9711b0fb3adcc37030d77429bddf6a08cee`. The published Maven JAR checksum was verified. The trial used the `python` generator with `--global-property models,modelDocs=false,modelTests=false` and `--additional-properties packageName=kochwiki_wire,hideGenerationTimestamp=true,disallowAdditionalPropertiesIfNotPresent=false`. The latter setting preserves schema-defined openness rather than closing every unspecified object. No custom templates, generated-source edits, or changes to the input contract were applied. Output and executable probes remained in a temporary trial directory; production resolver and tooling configuration were unchanged.

The trial ran 50 checks across Pydantic's `model_validate` and `model_validate_json`, generated `from_dict` helpers, amount union validation, serialization, and repeat generation. Thirty-one passed. Valid numeric and nullable success responses, empty collections, rejection of numeric strings and booleans in numeric response fields, invalid unit rejection, wire serialization with aliases, and byte-identical Python source across two generation runs passed. Direct Pydantic validation correctly required nullable fields to be present.

Blocking failures remain. Closed response objects lack `extra="forbid"`, so both direct validation paths and generated helpers accept undocumented fields at the presentation, ingredient, step, and foodstuff levels. Generated `from_dict` fills missing required nullable fields with `None` instead of rejecting omission. The generated `Amount` union accepts `"not-a-number"`, losing the request schema's decimal-string pattern. Direct Pydantic validation of a valid resolver request rejects a primitive amount because it expects an `Amount` wrapper object; direct validation of valid 422 issues likewise rejects primitive string/integer location entries because it expects `LocationInner` wrappers. Generated helpers handle those wrapper conversions and preserve extensible 422 fields, but their missing-field and extra-field behavior prevents treating them as strict contract validators. Generated code also includes `Any` and untyped helper parameters, requiring attention under the repositories' strict typing rules.

Stock OpenAPI Generator 7.25.0 Python output is therefore not adopted. Determinism alone does not establish fidelity; the same boundary probes must pass before model generation is delivered. The trial does not establish that every OpenAPI Generator version or Python generator variant has these limitations.

### datamodel-code-generator comparison

An isolated follow-up trial used datamodel-code-generator 0.83.0, Pydantic 2.13.5, and Ruff 0.16.9 against the same complete pinned snapshot. The input's SHA-256 matched AI Service's checked-in export. The CLI settings were `--input-file-type openapi --output-model-type pydantic_v2.BaseModel --target-python-version 3.12 --strict-types str bytes int float bool --strict-nullable --use-annotated --use-object-type --disable-timestamp --no-allow-remote-refs --strict-refs --ignore-pyproject`. No input schema, custom template, production dependency, or resolver code was changed. Trial sources, reports, and resolved dependency versions remain in the temporary directory `kochwiki-datamodel-generator-trial`.

The comparison reused the previous boundary cases through `model_validate` and `model_validate_json`; this generator has no `from_dict` helper. Amount cases validate the primitive through the generated resolver ingredient model rather than a generator-specific wrapper helper. The 36 equivalent checks passed with schema defaults. Expanded checks additionally protect every nullable response property, nested nullable foodstuff fields, closed request objects, request serialization with non-null preparation time and integer/fractional/string amounts, decimal-string patterns, strict error locations, and preservation of error extensions. Acceptance and preservation are separate assertions: default Pydantic configuration accepts schema-open error extensions but discards unknown fields. The unconstrained `ValidationError.input` also remains `Any` despite `--use-object-type`.

Supported configuration resolves those gaps without changing generated source. A deterministic `--extra-template-data` file derives each object model's `config.extra` from the schema: `forbid` for `additionalProperties: false`, otherwise `allow` for this snapshot's open objects. A global `--extra-fields allow` is unsuitable because it overrides closed objects too. A scoped `--type-overrides` file maps `ValidationError.input` to `builtins.object`, preserving arbitrary JSON values without `Any`. `--formatters ruff-check ruff-format` removes the generator's otherwise unused `Any` import. Future schema changes must still govern this configuration; typed additional-property schemas require preserving their value constraints rather than treating every non-false value as unconstrained.

With that configuration, all 81 expanded checks passed, including preservation of nested `ctx`, `input`, and unknown issue/envelope fields, no `Any` in the output, and byte-identical source across two runs with different input and output directories. Generation ran on Python 3.14.7 while targeting Python 3.12 syntax; supported-runtime and cross-platform checks remain part of delivery. Request numeric branches retain their bounds and decimal-string branches retain their regex. Strings such as `"0"` and `"-1"` remain accepted because the exported string branch permits them; backend business validation remains authoritative. These are fidelity checks against the exported contract, not a claim that generated requests reproduce every backend validator.

### Former generator decision (superseded)

Before direct model sharing was chosen, datamodel-code-generator 0.83.0 was selected with the trialled settings, schema-derived object policy, scoped unconstrained-input override, and Ruff 0.16.9 formatting for the proposed third step. The configured output passed all 81 trial checks without custom templates or generated-source edits. Its focus on Pydantic model generation fit that model-only boundary with the existing HTTP transport. [Pydantic's official documentation](https://docs.pydantic.dev/latest/integrations/datamodel_code_generator/) explicitly documents the tool for OpenAPI model generation, providing an additional ecosystem signal; observed contract fidelity was the primary reason for selection. That generator adoption decision is now superseded, not invalidated by a failed trial. The results do not establish that OpenAPI Generator is unsuitable for other SDK use cases or configurations.

The former delivery direction would have required deterministic resolver/reference selection, a locked generator environment, offline generation and drift commands, and permanent contract regression tests. Those generation tasks are no longer planned. Supported-runtime and cross-platform verification, consumer migration, and CI protection remain necessary for the shared-model package.

## Open Questions

- How should Angular present a malformed successful response, distinct from a 404, a 422, or a network failure?
- What version/tag convention, release trigger, artifact provenance, and future scope beyond the resolver should the producer-owned wheel use?
- How should shared models distinguish legitimate backend construction from strict JSON validation, and which request coercions should be deliberately removed?
- What Python/Pydantic versions should the package support, and which consumer type-checking and package compatibility checks should gate upgrades?
- Does future independent contract verification need an OpenAPI snapshot in AI Service, beyond the installed package and actual resolver integration tests?
- How should CI run producer/consumer compatibility tests against the pinned public GitHub revision with isolated environments and database fixtures?
- What deployment ordering or compatibility window is required for future incompatible resolver changes, and is automatic upstream freshness monitoring needed?

## Risks

- Generated output can faithfully reproduce inaccurate OpenAPI. Route behavior and schema need contract-level checks before generation becomes a gate.
- Adding validators to every response increases browser code. Strict fixed-object validation also makes an additive backend field a runtime error until the frontend contract is updated and deployed with it.
- Strictly generated DTOs may expose existing request-type shortcuts and UI assumptions, requiring focused adapters rather than a wide refactor.
- A snapshot can remain reproducible while falling behind upstream; provenance checks must not be reported as proof of latest-version compatibility.
- Shared backend models currently permit coercions that generated wire validators reject. Extraction must tighten consumer parsing without breaking backend construction, serialization, or expected request behavior accidentally.
- A released package can drift from the deployed API even when its source models are shared with Kochwiki. Explicit upgrades and deployment coordination remain necessary.
- Replacing AI Service's internal presentation models directly with shared wire models could change retained proposal behavior. The explicit mapping boundary protects these internal requirements.

## Summary

Kochwiki owns shared Pydantic API models in a standalone package and imports those same definitions into its backend. Publish versioned wheels through GitHub Releases for AI Service and future compatible Python consumers. Continue exporting OpenAPI from the models and routes for Angular's generated types/validators and other consumers. AI Service validates at its HTTP boundary using the package and maps into its internal proposal models; endpoint wiring remains manual. Consumer-owned OpenAPI-to-Pydantic generation is rejected in favor of this direction, with its implementation and trial results retained as historical evidence. Protect strict validation, package provenance, supported dependencies, and actual producer/consumer compatibility through tests and CI; coordinate incompatible deployments.
