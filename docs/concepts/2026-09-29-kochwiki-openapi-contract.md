# Kochwiki OpenAPI Contract Generation

## Status

Draft under discussion. Agreed scope: every Kochwiki-owned FastAPI endpoint, including routes Angular does not currently call and the recipe-presentation resolver used by AI Service. Every Kochwiki JSON response consumed by Angular receives generated runtime validation. Fixed response objects reject undocumented fields, assuming coordinated backend and frontend rollout. The AI Service's conversation API contract concept is the baseline for the contract strategy, not an implementation dependency. FastAPI's default 422 shape is restored, domain 404/409 errors use `detail` and are declared in OpenAPI, `/meta/version` declares its plain-text response, and delete routes declare bodyless 204 responses. Checked-in TypeScript types and Zod Mini schemas now cover the complete Kochwiki OpenAPI document. Foodstuff CRUD uses generated request and response types and validates successful JSON responses. Foodstuff labels and unit choices are now owned by Angular; the metadata endpoints and fetching service have been removed. User selection and restoration now use generated types and strict runtime validation. Recipe list, active detail, and specific version loading now use generated response types and strict nested runtime validation. Recipe writes now use generated request types and validate all five JSON mutation responses; ambiguous write failures withhold success feedback and navigation.

The Angular contract migration and Kochwiki's CI generation gate are implemented. Kochwiki's resolver success schema is now closed at every object level, and its checked-in OpenAPI and Zod validators have been regenerated. The remaining resolver direction covers an OpenAPI snapshot, deterministic Python model generation, consumer integration, and compatibility checks in AI Service. Those consumer changes are not implemented; a Python generator has not yet been trialled or selected.

## Context

Kochwiki's FastAPI routes declare Pydantic request models and response models for recipes, foodstuffs, users, and the recipe-presentation resolver. FastAPI serves OpenAPI at `/api/openapi.json`. Angular calls Kochwiki through `/api` with `HttpClient` and now uses generated wire types and runtime validators. The resolver is also called by the separately deployed AI Service; the browser's `/ai/api/v1` conversation route is a relay to that service, not a Kochwiki backend API.

The AI Service concept establishes a useful pattern: backend models define the HTTP contract; the exported OpenAPI document drives checked-in TypeScript types and runtime validators; the transport validates received JSON while retaining its existing request and error behavior. Kochwiki has a different transport and audience, so that pattern needs adaptation rather than direct copying.

## Problem

Handwritten wire interfaces can drift from FastAPI's shapes. `HttpClient.get<T>()` asserts a type without validating the received body. Angular's former foodstuff create/update methods accepted `Partial<Foodstuff>` even though the backend uses separate create and update schemas; they now use generated request types. The foodstuff delete method previously promised a numeric response although the route returns 204 with no body; it now returns `Promise<void>`. AI Service's resolver still builds requests manually and validates responses against handwritten Python models.

Kochwiki now uses FastAPI's default request-validation response, `{ detail: [validation issues] }`, and returns domain 404/409 errors as `{ detail: string }`. Applicable domain errors are declared per route in OpenAPI. The HTTP status is carried by the response status line. FastAPI's generated validation-issue schema permits optional `input` and `ctx` and additional fields, so error validators must not impose the strict fixed-object policy used for Kochwiki-owned success DTOs. The plain-text version endpoint and bodyless 204 responses still need to survive generation with their actual media types and semantics.

## Proposed Direction

Treat Kochwiki's FastAPI models and route declarations as the source of truth for all Kochwiki-owned HTTP endpoints. Cover Angular-used routes, the recipe-presentation resolver consumed by AI Service, and currently unused routes such as recipe history, ingredient and step lists, and user mutations. Keep the AI Service conversation contract owned and generated in the AI Service repository; Kochwiki should use the published chat UI transport for that boundary rather than generate a second client from the relayed paths.

Make OpenAPI describe actual successful and expected failed responses before relying on generated output. Preserve FastAPI response validation on JSON success paths and its default 422 behavior. Model and validate domain error bodies sent through direct `JSONResponse`. Keep 204 responses bodyless and `/meta/version` as text. Check concrete route behavior against the exported document, especially recipe decimals, nullable values, and resolver responses.

Generate checked-in TypeScript request and response types from a reproducible `app.openapi()` export so Angular builds do not depend on a running backend. Replace handwritten wire interfaces at the backend service boundary, while keeping UI-only view models and mapping functions where they express actual presentation needs. Add the existing generation drift check to release/CI when the toolchain is available there. Hey API `0.99.0`, matching the AI Service's pinned version, passed the Kochwiki trial for decimal numbers, nullable responses, plain text, bodyless 204, and resolver types.

Use generated runtime validators for every Kochwiki JSON response consumed by Angular, after verifying they preserve the existing numeric, nullable, and nested recipe shapes. Reject undocumented fields on fixed response objects rather than silently stripping them. Allow dynamic keys only where the OpenAPI schema explicitly models a map. Validate before data reaches recipe editing, proposal mapping, and draft saving. Keep Angular `HttpClient` and the existing service methods; generating a full HTTP client is not needed to eliminate duplicate models and unchecked responses. Classify malformed success bodies separately from HTTP failures without weakening the current 404/422 handling. The exact validator integration and UI error behavior remain to be decided. The plain-text version endpoint and bodyless 204 responses do not pass through JSON validators.

## Contract Boundaries

- Kochwiki owns recipe, foodstuff, user, version metadata, and recipe-presentation resolver shapes. The AI Service owns session, message, turn, and proposal-envelope shapes. The Nginx and Angular relays do not create a new contract source.
- The resolver is a service-to-service contract and deserves explicit coverage even if Angular does not call it directly. Its request and enriched response must agree with AI Service's expectations; generated Angular types alone cannot establish that.
- Backend and Angular changes in this repository roll out together. Strict response validation assumes neither side will serve an incompatible version during deployment. The resolver has a separate deployer and may need coordinated rollout when its wire shape changes.
- HTTP DTOs and UI domain models may differ. Generated types should replace duplicate wire definitions, not force backend-specific names and optionality through every component.
- Runtime validation checks JSON shape; it does not prove business rules, authorization, or that an AI proposal is safe to save. Proposal artifact validation remains at the AI Service boundary and Kochwiki's proposal-to-draft mapping.

## Alternatives Considered

- **Keep handwritten models and add contract tests:** small tooling cost, but dual definitions and unchecked HTTP responses remain.
- **Generate TypeScript types only:** catches compile-time drift but leaves runtime JSON unchecked. This may be a useful first delivery slice, not the complete direction.
- **Generate a full client:** would replace established Angular services and complicate their change notifications and error handling without a clear contract benefit.
- **Generate types and validators:** matches the AI Service baseline and addresses both drift and runtime shape checks, at the cost of generator workflow and browser dependency weight.

## Integration Impact

FastAPI now owns the 422 response body and OpenAPI schema. Kochwiki's domain error handler validates its shared `{ detail: string }` model, and routes declare applicable 404/409 responses. The foodstuff delete service represents its bodyless 204 as `void`. Contract tests cover `/meta/version` as `text/plain`, all delete routes as bodyless 204, and representative decimal and resolver JSON against OpenAPI response schemas. Generate the checked-in export and types from `frontend` with `npm run generate:kochwiki-contract`; verify drift with `npm run check:kochwiki-contract`. The generator uses the backend virtual environment when present, or `PYTHON`/system Python, and fixes the export's version metadata at `0.0.0` to avoid environment-dependent output.

The Angular service boundary is the natural place to consume generated types and validators. The complete backend contract is generated even for routes Angular does not currently call; runtime validation will apply wherever Angular actually consumes Kochwiki JSON. Foodstuff CRUD now follows the backend's distinct create/update models. Foodstuff field labels and unit choices live in Angular; choices use an exhaustive mapping against the generated Unit type. Recipe and presentation consumers can retain narrow adapters where a UI-only shape is useful. The generation drift check runs locally and as a required job before both image builds in the PR and release workflow. Inspired by AI Service's publish workflow, the job installs pinned backend requirements with Python 3.13 and locked frontend dependencies with Node.js 24, supplies the existing short-lived GitHub token for the private chat UI package, and runs `npm run check:kochwiki-contract`. Stale or missing generated files prevent image building and publishing; generation requires no running backend or database.

Foodstuff list, get, create, and patch responses now enter Angular as `unknown` and are parsed using generated Zod Mini schemas before the service resolves. `FoodstuffSummaryOut` and its `FoodstuffOut` subclass declare `extra="forbid"`, exporting `additionalProperties: false`. Hey API 0.99.0's default Zod object resolver ignores this constraint; a generator resolver emits `strictObject` for schemas whose parsed additional-properties type is `never`. The policy follows the backend schema rather than applying strictness to every generated object. Zod is pinned at 4.4.3. The generation and drift scripts include `zod.gen.ts`.

The shared `requestApiResponse` helper accepts the HTTP method, URL, response schema, and optional request body. It uses the same method and URL for `HttpClient.request<unknown>()` and contract-error diagnostics, preventing drift between the request and error description. All currently validated foodstuff CRUD calls use this helper. A malformed successful foodstuff response rejects with `ApiContractError`, identifying the method and complete request URL, with validation issues as its cause. HTTP failures retain Angular's `HttpErrorResponse` and original bodies, including 404, 409, and 422. Existing UI failure messages remain generic; the dedicated contract error is available for diagnosis. Delete responses remain outside JSON validation. Tests cover numeric and nullable values, recipe UUIDs, empty lists, missing fields, incorrect types, undocumented fields, and preservation of HTTP failures.

Foodstuff field labels and unit display labels are owned by the frontend. The form and table share typed mappings to German display strings; the label component and its template `i18n` markers have been removed. The field and unit mappings are exhaustive against the generated `FoodstuffCreate` keys and `Unit` type, so adding a backend field or unit requires a frontend label when regenerated. Both foodstuff metadata endpoints, their response schemas, and the frontend fetching service have been removed; labels and choices are available without a metadata request or fallback. The unused Angular localization dependency and initialization have been removed; translated locale builds are not configured. The shared `unitVerbose` response field remains in foodstuff, recipe, and resolver contracts for existing consumers, while the foodstuff table displays its local unit label. Tests cover local form labels, unit selection and wire values, and table rendering independent of backend unit display text. Tests specific to the removed metadata routes and service were removed as obsolete.

The generated `FoodstuffUpdate` type permits `name: null` and `unit: null` because Pydantic's field schema does not express its model-level rejection of those values. The service's current form supplies non-null values, but callers of the generated update type still need the backend's 422 handling. Foodstuff, user, recipe, and resolver success DTOs now forbid additional fields.

The user selection and restoration slice is implemented. `UserBackendService` uses generated `UserOut` and `UserCreate` types and validates list, get, and create responses through `requestApiResponse`. `UserOut` forbids additional fields, and the generated validator follows that policy. Frontend consumers import the generated `UserOut` type directly; no alternate user type alias is maintained. The creation form supplies a non-null typed request without a cast. Local storage owns an independently validated `{ id }` selection record; usernames and other user data remain transient. Restoration fetches and validates the current user before activating the selection. The app displays a loading state while guarded navigation waits. A 404 clears the stored ID and guarded navigation redirects to user selection. Network and contract failures retain only the ID, leave the user inactive, and show retry and alternative-selection actions. Retry preserves the requested route. Request tokens prevent stale responses from restoring a user after switching or selecting again, including the same user. Older stored records are reduced to their ID on load. Tests cover malformed responses, preserved HTTP errors, validated restoration, pending route activation, retry, deleted users, stale restoration, and creation failure without closing the dialog or announcing a created user. Recipe migration, dedicated contract-error messaging, and CI/tooling changes remain outside this slice.

The recipe loading slice is implemented. `RecipeBackendService` validates recipe list, active detail, and specific version GET responses through `requestApiResponse`. `RecipeVersionOut`, `IngredientOut`, and `StepOut` forbid additional fields; nested foodstuff summaries already follow that policy. Consumers import generated response and state types directly, replacing handwritten response interfaces without aliases. The readonly recipe-presentation view models remain separate; recipe write models were subsequently migrated to generated types. Recipes loaded into the list, detail page, editor, or conversation pass runtime validation before use. Tests cover decimal numbers, independent nullability, UUIDs, timestamps, nested malformed data, undocumented fields, empty lists and recipes, and preserved HTTP errors. Existing page error behavior remains: an initial detail failure shows the error header, snackbar, and recipe-not-found placeholder; a failed list refresh retains the previously validated data. Dedicated contract-error messaging remains open. The subsequent recipe write slice completes request migration and mutation-response validation; resolver coordination and tooling changes remain outside these slices.

The recipe write slice is implemented. Create, publish active edit, create draft, update draft, and publish draft responses use `requestApiResponse` with the existing strict `RecipeVersionOut` validator. Services, editor submissions, and proposal-to-draft mapping use generated `RecipeVersionWrite`, with generated nested `IngredientWrite` and `StepWrite`; the three duplicate handwritten write interfaces have been removed without aliases. The editor and proposal mapping still send complete payloads with numeric amounts and explicit nullable metadata, although the generated request contract also permits omitted defaults and decimal strings. Deletes remain bodyless `Promise<void>`. Declared HTTP 404/409/422 rejections retain the existing dialog failure messages; other failures conservatively remain unconfirmed, including HTTP 408 timeouts. Contract failures, connection failures, and server failures report that the write could not be confirmed and may already have happened. Create and edit dialogs stay open with their input intact, release their submission lock, and withhold success notifications, change announcements, and navigation. Draft publication likewise withholds success navigation; AI draft saving retains its existing unconfirmed-save feedback without an open-draft action. Writes are not retried automatically. Tests cover all five request paths and payloads, strict nested response validation, preserved HTTP failures, connection failures without retry, dialog failure behavior, publication feedback, and an actual malformed HTTP response during AI draft saving. A manual retry can still create another recipe or version; ambiguous dialog feedback asks the user to check the recipe list first. Idempotency and automatic reconciliation remain outside this slice.

The AI Service calls Kochwiki's resolver through its configured `KOCHWIKI_BASE_URL`; its conversation package's generated contract covers `/ai/api/v1` after relay. The resolver integration below establishes a separate generated Python consumer boundary owned by AI Service and sourced from Kochwiki's OpenAPI.

## Resolver Integration Direction

Deliver the resolver contract as one coherent direction across both repositories: accurate producer schemas, a versioned OpenAPI snapshot, deterministic Python wire models, consumer migration, and CI protection. Kochwiki remains authoritative for the resolver request, success response, and declared errors. The first step is implemented: `RecipePresentationOut`, `RecipePresentationIngredientOut`, and `RecipePresentationStepOut` now forbid additional fields, matching nested foodstuff summaries and resolver request objects. The wire fields, numeric serialization, required nullable values, and empty collections remain unchanged. Kochwiki's checked-in OpenAPI and generated Zod validators reflect the closed schemas. Regression tests cover rejection of undocumented fields at every response level, preserved numbers and nulls, required nullable fields, and actual endpoint responses. AI Service snapshot and generator tooling remain subsequent work.

AI Service will check in the complete reproducible Kochwiki OpenAPI export together with its source commit. Snapshot updates are explicit and reviewable. Ordinary generation and builds use that local snapshot rather than fetching a moving upstream schema or requiring a running Kochwiki backend. Provide separate snapshot-update, model-generation, and drift-check commands. Generate the resolver request, response, declared error models, and their referenced schemas through deterministic selection from the complete snapshot, without handwritten copies of those wire definitions or a generated full HTTP client.

Pin the Python generator and its tooling dependencies, disable variable timestamps and paths in output, and check generated sources into AI Service. `datamodel-code-generator` is a candidate for OpenAPI-to-Pydantic v2 generation, not a selected dependency. A trial must verify reproducible output, numeric decimal responses, integer and fractional values, required nullable fields, nested collections, enums, and rejection of undocumented fields where the source schema forbids them. FastAPI's extensible validation-error fields must retain their documented openness rather than inherit a blanket strict-object policy. Generated validation must reject malformed JSON types rather than silently coerce them. OpenAPI does not express every backend business validator, so generated request models do not replace backend validation.

Migrate AI Service's resolver HTTP boundary to construct outgoing payloads with generated request models and validate incoming bodies with generated response models. Preserve its timeout and HTTP error classification behavior, including non-retryable 404/422 outcomes. The existing handwritten presentation models also serve as immutable proposal data, use tuple collections, and impose bounds absent from Kochwiki's response schema. Retain them as explicitly internal models and map validated wire responses into them. Keep internal constraints and proposal serialization stable; do not expose generated model naming, collection mutability, or weaker wire constraints throughout the proposal pipeline. Internal mapping failures must remain controlled resolver failures.

CI must check that generated Python models match the snapshot and that the snapshot matches the recorded Kochwiki revision. Compatibility tests must exercise the actual Kochwiki resolver with requests produced by the AI Service consumer and validate returned bodies through that consumer, covering decimals, independent nullability, empty and nested collections, and expected errors. Add malformed-response tests for missing fields, incorrect types, and undocumented fields, and verify that migration preserves proposal behavior. Test repositories in isolated environments so their identically named Python `app` packages do not collide. The exact cross-repository checkout and test mechanism remains to be selected; CI should gate AI Service image builds and publishing on these checks.

Checking the recorded upstream revision proves provenance and reproducibility, not freshness against Kochwiki's latest revision. Advancing that revision is an explicit contract update that reruns generation and compatibility checks. Incompatible resolver changes require coordinated producer and consumer deployment; snapshot pinning alone does not make mixed deployed versions compatible. Automatic upstream monitoring and any compatibility window remain separate decisions, rather than implicit live-schema fetching during builds.

## Open Questions

- How should Angular present a malformed successful response, distinct from a 404, a 422, or a network failure?
- Which pinned Python generator and configuration pass the resolver contract fidelity and determinism trial?
- How should CI retrieve the recorded Kochwiki revision and run producer/consumer compatibility tests with isolated environments and database fixtures?
- What deployment ordering or compatibility window is required for future incompatible resolver changes, and is automatic upstream freshness monitoring needed?

## Risks

- Generated output can faithfully reproduce inaccurate OpenAPI. Route behavior and schema need contract-level checks before generation becomes a gate.
- Adding validators to every response increases browser code. Strict fixed-object validation also makes an additive backend field a runtime error until the frontend contract is updated and deployed with it.
- Strictly generated DTOs may expose existing request-type shortcuts and UI assumptions, requiring focused adapters rather than a wide refactor.
- A snapshot can remain reproducible while falling behind upstream; provenance checks must not be reported as proof of latest-version compatibility.
- Replacing AI Service's internal presentation models directly with generated wire models could weaken constraints or change retained proposal behavior. The explicit mapping boundary protects these internal requirements.

## Summary

Use Kochwiki's FastAPI OpenAPI document as the authoritative Kochwiki HTTP contract and derive Angular wire types and runtime checks from it. AI Service will derive its resolver wire models from a checked-in snapshot of that same document, validate at its HTTP boundary, and map into its internal proposal models. Keep the AI Service conversation contract owned by its repository, and protect resolver generation, provenance, and actual producer/consumer compatibility through CI.
